## Core Projects (TrueMotive Triad)

### truemotive-desktop
- **Project type**: Tauri 2 desktop application restructured to a non-Tauri native window around a web UI
- **Architecture pattern**: Native window around web UI, restructured without the Tauri runtime; legacy references preserved as legacy artifacts
- **Sidecar pattern**: Historically used a "managed sidecar" backend pattern where the backend ran as a separate process; adjusted in the restructured application to operate as a standalone service architecture
- **Configuration hierarchy**: `default.json` provides baseline appearance settings (`theme: "studio"`, `mode: "dark"`); themes extend or override defaults; profiles system (only `example.json` exists)
- **Script-driven builds**: Node.js scripts used for build processes, sidecar management, and deployment. Key scripts: build-linux-arm64.sh, build-windows-bundle.sh, deploy-compose.sh
- **Code structure**: Organized into apps/, config/, reports/, scripts/, services/
- **Key finding**: Restructuring from Tauri was completed; the application no longer requires the Tauri runtime but configuration artifacts are preserved as legacy references
- **Media graph database**: `media-graph.sqlite` stores media assets, channel data, and related state
- **Monitoring**: Visible in the CPU/MEM meters dashboard
- **TMD listener**: `TMD_HOST=127.0.0.1`, `TMD_PORT=4712` (loopback, always)

### mediamesh
- **Project type**: Media mesh coordination layer connecting the three triad projects; provides Grafana-based monitoring interface
- **Architecture pattern**: Media mesh coordination layer with Grafana integration. Acts as the media coordination layer between truemotive-desktop (media graph database) and occc-ui (monitored service)
- **Code structure**: Configuration files, scripts/ (build-rist-receiver-dante.sh, edge.sh, seed-media.sh, start-all.sh, etc.), web/ (Vite-based frontend), edge/ (NPM proxy configuration), compose files (docker-compose.yml and overlays)
- **Key architecture decisions**:
  - **Media Coordination Layer**: mediamesh enables communication and data sharing between the three projects in the TrueMotive triad
  - **Grafana Monitoring Integration**: Integrates with Grafana for monitoring and UI purposes, with access keys documented in architecture screenshots
  - **Cross-Project Data Flow**: Facilitates data flow between truemotive-desktop and occc-ui, serving as the media mesh component of the overall architecture
- **VITE_MEDIAMESH_URL**: Baked into occc-ui at build time, pointing to port 8443 for the mediamesh backend
- **Channel coordination**: Three kinds of channel flow (built, authored, example); lifecycle: compile → start → HLS output → viewer (occc-ui)
- **Monitoring**: Monitored with Grafana integration active

## Key Architectural Patterns (Cross-Cutting)

1. **Web UI First**: All three triad projects deliver their primary UI through web technologies. The desktop (`truemotive-desktop`) is a native wrapper around web views; `mediamesh` and `occc-ui` are both web-based applications.

2. **Configuration Hierarchy**: Consistent across all projects: `default.json` → `themes/` → `profiles/`. `default.json` provides baseline appearance settings (`theme: "studio"`, `mode: "dark"`). Themes define color schemes with dark and light variants using tokens: bg, panel, raised, panelLine, lineStrong, ink, inkDim, inkFaint, accent, onAccent, live, crit, warn, good. Profiles suggest a profile-based customization system; only `example.json` exists.

3. **Script-Driven Builds**: Heavy use of Node.js scripts for configuration, build processes, and deployment across all three projects. Per-host differences live in `.env` files; hosts have no local edits to tracked files.

4. **Triad Data Flow Sequence**: Contributor → RIST/SRT/RTMP/WebRTC → Engine (Liquidsoap) → HLS / WHEP → occc-ui (viewer), with mediamesh facilitating coordination + Grafana monitoring, and `truemotive-desktop` serving as the media graph + appearance config.

5. **MCP Coordination**: The MCP endpoint (`/mcp`) reaches the engine through the front door (TMD), not through direct ports.

## Coordination Mechanisms

1. **MCP endpoint** (`/mcp`): Reaches engine through the front door (TMD), not through direct ports. Verified on mahoney-mac (2026-11-24).

2. **VITE_MEDIAMESH_URL**: Baked into occc-ui at build time, pointing to port 8443 for the mediamesh backend. Also referenced by truemotive-desktop for API calls.

3. **Media graph database integration**: truemotive-desktop's `media-graph.sqlite` stores media assets, channel data, and related state, integrated with the mediamesh coordination layer.

4. **Channel lifecycle**: compile → start → HLS output → viewer (occc-ui). Three kinds of channel flow: built, authored, example. Coordination pattern validated per ARCHITECTURE.md Sections 5–11.

5. **MediaMTX integration points** (3 relationships):
   - **Ingest**: RIST/UDP ingest on ports 9000, 9100; SRT on 9300–9399; RTMP on 1935
   - **Egress**: HLS on engine port 8888; WebRTC playback on mediamtx port 8889; RIST/SRT/RTMP output
   - **Direct browser preview**: mediamtx WHEP listener on :8889 with `MTX_WEBRTC_ADDITIONAL_HOSTS` for browser access

6. **Cross-project configuration consistency**: Configuration hierarchy (default.json → themes → profiles) and script-driven build patterns remain consistent across the triad projects.
